# 06 · How the system knows itself

*From three design notes of September 2026: how a rule-based system can see its own structure, how skills are organised without a registry, and a taxonomy of facts that decides what may live in prose.*

## The problem

A workbench made of prompts, rules, skills and hooks grows a lot of text that claims to describe itself: "this skill depends on that one", "this rule is loaded by every session", "these files form the memory organ". None of those claims is checked by anything, and in the private workbench a measurement in late September 2026 showed what that costs: of about 130 skills, roughly twenty had been loaded by any session in the previous thirty days, and about 99% of the context window in a typical session was tool output, not the rules the system believed it was running on.

The design response has three parts: measure what is loaded, derive structure from consumers instead of declaring it, and limit what prose is allowed to hold.

## Three kinds of edge

| Edge | Example | How it is known |
|---|---|---|
| **reference** | a document names another document | written by an author; a claim |
| **call** | a skill invokes a tool or another skill | observed from the run log |
| **write-set** | a session touched these paths | observed from the ledger |

Only the last two are facts. A reference edge is true when it was written and nothing keeps it true afterwards.

## Load trace: coverage for prompts

Coverage, in testing, tells you which lines of code a test actually executed. The same idea applies to prompts: for each rule, skill or document, how many sessions in the last thirty days actually loaded it into a prompt. The ledger gives the answer without anyone declaring anything.

The first trace in the private workbench showed that the self-declared dependency lists had zero readers: no prompt, skill or check ever consumed them. They were documentation pretending to be structure. Two changes followed.

- **Reverse-derived edges.** In-edges are computed from who actually loaded what, never written by hand. "Which sessions used this rule" is a query over the ledger, not a field in the rule.
- **An orphan gate.** A rule, skill or document with no readers over the window fails a check. It is either wired to a consumer or deleted. Keeping it costs context in every session that loads the directory and teaches the agents that rules are optional.

**Truth lives on the consumer side.** A rule exists only if some prompt loads it. A dependency exists only if something breaks without it. The only remaining falsifier for "this rule matters" is a behaviour A/B: run the same task with the rule loaded and without it, and look for a difference. If there is none, the rule is prose.

Useful analogies for the same move elsewhere: tree shaking (a bundler drops code nothing imports), feature-flag telemetry (a flag nobody evaluates is dead), data lineage (a column's consumers are discovered from query logs, not from a spreadsheet), and test coverage itself.

## Skills without a registry

A skill is its folder: one instructions file, optional helper files, and the open-standard frontmatter the host already reads. There is no registry, index or catalogue of skills, because every such list in the workbench's history drifted within weeks.

Three mechanisms replace the registry:

1. **An overlap check at creation.** Before a new skill is written, the existing ones are searched for the same job. The decision (extend, compose, replace, create) is recorded.
2. **A required caller.** A hook refuses to admit a skill that nothing invokes. The caller can be a person's slash command, another skill, or an agent definition, but it must exist.
3. **Open-standard frontmatter only.** The skill's name, description and trigger phrases are in the host's own format. No parallel metadata the host cannot read.

A derived index is allowed only when some consumer demonstrably breaks without it. The test is mechanical: delete the index, run the consumer, watch. If nothing fails, the index is not admitted.

## A taxonomy of facts

Every fact in the system is one of three things, and the three have different rules.

| Kind | What it is | Rule |
|---|---|---|
| **Single source of truth** | The one place a fact is authoritative: a config value, a frontmatter field, a ledger line | Written once; everything else derives from it |
| **Derived view** | An index, a count, a graph, a dashboard | Generated by a command; never hand-edited; can be deleted and rebuilt |
| **Machine legibility** | The structure that lets a program read the fact: frontmatter schema, a JSON line, a file naming rule | Validated at write time |

Four questions decide where a new fact goes:

1. Does a program need to read it? If not, it is prose and goes in a note.
2. Does it already have a source? If so, derive from that source; never create a second copy.
3. Can a command produce it? If so, it is a derived view and is generated, not maintained.
4. Does its absence break a consumer? If not, it is not admitted as structure.

**Query first.** A number in a document is a claim unless it carries its provenance: the command that produced it and the date. "Twenty skills loaded in thirty days" is admissible because a query over the ledger produced it on a stated day. "Most skills are unused" is not.

**Prose may hold only four things:** where authority lives, how to query it, why a rule exists, and the invariants. Everything else prose tends to hold (inventories, dependency lists, counts, current status) rots, and the rot is invisible because prose never fails a check.

## Three beats of governance

Checks run at three rhythms, each catching what the previous one cannot see.

| Beat | When | What it can see | Example |
|---|---|---|---|
| **Write time** | every file write, by hook | the one file being written | frontmatter schema, a path literal outside config, a forbidden write target |
| **Commit time** | every commit | the whole diff | cross-file consistency, the diff-size review gate, link existence |
| **Periodic sweep** | weekly, or on demand | the whole repository and the ledger | orphans, stale pages, contradictions, drift between a rule and its enforcer; the person reads the report |

The sweep is the only beat with a human in it, and the only one allowed to use semantic judgment. The first two are mechanical and blocking.

## Prosthetics for model weaknesses

Language models are reliably bad at a short list of things, and the system treats each with a tool rather than a reminder.

| Weakness | Prosthetic |
|---|---|
| Counting | a command counts; the model reports the command's output |
| Arithmetic | a calculator or a script, never mental math in prose |
| Exact retrieval | grep and the index, never "I recall that…" |
| Dates | the ledger's timestamps; relative dates are converted to absolute on write |
| Long lists | a file the model reads back, never a list held in context |
| Semantic deduplication | an embedding similarity pass, with a person confirming merges |

The pattern is the same as the rest of this document: where the model's self-report is unreliable, the system does not ask for a better self-report. It routes the question to something that cannot be wrong in that particular way.
